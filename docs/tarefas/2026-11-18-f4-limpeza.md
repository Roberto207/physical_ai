## 4. Checklist para o PC do laboratório

Siga na ordem. Depois de cada item, anote o resultado num documento novo em `docs/tarefas/` (DOC-04).

1. **Atualizar o código:** `git pull` (depois do push dos commits locais; ver a seção 5).
2. **V1, build e tags Jazzy:** `infra/docker/construir_imagem.sh base robo sim`.
   - Esperado: as linhas `Guardada: physical-ai:base (jazzy) -> physical-ai:jazzy-base`, e o mesmo para `robo` e `sim`. No fim, `ROS_DISTRO da imagem nova: humble`.
   - Anote o tamanho (`docker images 'physical-ai'`) e o tempo.
3. **SEG-01 sem robô** (robô desligado ou fora da rede):
   - `docker tag physical-ai:jazzy-base physical-ai:base && infra/docker/lab.sh robo estado` deve responder `RECUSADO (SEG-01)` com o código 1;
   - depois, para voltar: `infra/docker/construir_imagem.sh base` (o cache torna isso rápido).
4. **Fumaça do Gazebo (SIM-01, F2):**
   - `infra/docker/lab.sh sim subir gazebo` e, depois de 90 s, `infra/docker/lab.sh sim compose run --rm ferramentas ros2 topic echo --once /scan` (repita com `/odom`, `/tf`, `/dock_status`; `/battery_state` pode levar mais);
   - `infra/docker/lab.sh sim compose exec gazebo pgrep -af 'ign gazebo'`: não pode haver o processo de GUI.
5. **Mapa no Gazebo** (repete o 16/11): `subir gazebo slam rviz`, `undock`, `teleop`, `salvar teste_maze_humble`.
6. **V3 e os 11 cenários L1:** `infra/docker/teste_l1.sh ciclo`, depois os outros 10. Todos com `APROVADO`.
7. **V5, robô real: só com a sua permissão, no dia.**
   - Documentação: [Discovery Server](https://turtlebot.github.io/turtlebot4-user-manual/setup/discovery_server.html) e [Generating a map](https://turtlebot.github.io/turtlebot4-user-manual/tutorials/generate_map.html), aba Humble.
   - Passos: `lab.sh robo checar-rede` (`REDE OK`), depois `lab.sh robo subir slam rviz`, com `journalctl -u turtlebot4 -f` aberto no robô (`ssh robo`) por 5 min, sem `Bad alloc` nem `oom-kill`.
   - Só depois disso o DOC-01 tira os avisos "não use o `lab.sh robo`".
8. **A medição M-GZH** fica fora desta lista: só com pedido explícito.

Se algo falhar, o primeiro lugar para olhar é o log do entrypoint: `COMPILAR_WS` mostra o `colcon.log` inteiro quando a compilação falha.
