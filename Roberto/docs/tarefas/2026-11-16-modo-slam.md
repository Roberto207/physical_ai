## 1. Resposta direta

Agora existe um comando, `infra/docker/slam.sh`, com dois modos:

- **`sim`**: treino no Gazebo (mundo `maze`), dentro de uma rede isolada.
- **`robo`**: o robô de verdade, com a rede do PC.

Nos dois, o caminho é o mesmo: subir o SLAM, abrir o RViz, dirigir devagar pelo teclado e salvar. O mapa sai em `workspace/mapas/` com três arquivos (`.yaml`, `.pgm` e uma ficha `.info.txt`) e passa na hora pelo nosso `conferir_mapa`. Esse é o mapa que o `inf_lab.yaml` da patrulha vai apontar.

Por baixo, o script só roda os comandos da documentação oficial do TurtleBot 4. Ele não inventa nenhum passo. Também não faz dock nem undock no robô real e não muda nada na rede ou na configuração do robô.

## 2. O exemplo do dia a dia

Pense em fazer a **planta baixa de uma casa nova andando por ela com uma trena a laser**. Você entra pela porta da frente (a doca), anda devagar por todos os cômodos, e a trena vai desenhando as paredes. No fim, você salva o desenho. Depois disso, qualquer pessoa consegue dizer "vá até a cozinha" apontando um lugar na planta.

| Na casa | No robô |
|---|---|
| A trena a laser | O lidar do robô (tópico `/scan`) |
| Contar os passos | A odometria das rodas (`/odom`) |
| O desenho que vai se formando | O SLAM (`slam_toolbox`), que publica o `/map` |
| Andar devagar por todos os cômodos | O teleop a 0,15 m/s |
| Começar pela porta da frente | Começar com o robô na doca (hipótese H3): a doca fica em (0, 0) |
| Salvar a planta | `salvar`, que grava o `.yaml` e o `.pgm` |
| Conferir se a planta não saiu borrada | `conferir_mapa`, e você olhar a imagem |

**SLAM** quer dizer *Simultaneous Localization and Mapping*: o robô faz o mapa e, ao mesmo tempo, descobre onde está nele. É diferente da **localização** (AMCL), que a patrulha usa depois. A localização recebe um mapa pronto e só descobre onde o robô está.

## 3. O pipeline, peça por peça

A ordem abaixo é a ordem em que as peças são usadas no laboratório.

### 3.1 Construir a imagem no PC do lab

| | |
|---|---|
| **Onde** | `infra/docker/construir_imagem.sh` (novo) e `infra/docker/Dockerfile` (alterado) |
| **O que faz** | Confere se a máquina tem pelo menos 12 GiB de RAM e roda `docker build -t physical-ai:jazzy` |
| **Para quê** | O GitHub leva o Dockerfile, mas não a imagem. O PC do lab precisa construí-la uma vez |
| **Por que assim** | O `docker build` não tem teto de memória. Ele já travou o seu notebook (7,4 GiB) em 5/nov. Com a conferência, o mesmo script recusa no notebook e roda no PC do lab |

No Dockerfile, entraram `ros-jazzy-slam-toolbox` e `ros-jazzy-teleop-twist-keyboard`. O `slam_toolbox` já vinha como dependência do `turtlebot4_navigation` (conferido no `package.xml` do ramo `jazzy`). Mesmo assim, ficou explícito: se um dia a dependência mudar, a imagem não quebra sem aviso.

### 3.2 Dizer ao PC como achar o robô na rede

| | |
|---|---|
| **Onde** | `infra/lab/rede_lab.env` (novo) |
| **O que faz** | Define `ROS_DOMAIN_ID=0` e `RMW_IMPLEMENTATION=rmw_fastrtps_cpp`. O `ROS_DISCOVERY_SERVER` fica comentado |
| **Para quê** | O PC e o robô só se enxergam se usarem o mesmo "canal" (o domínio) e o mesmo "idioma" (o middleware DDS) |
| **Por que assim** | É o que o manual pede para o PC, na aba Jazzy: [Simple Discovery](https://turtlebot.github.io/turtlebot4-user-manual/setup/simple_discovery.html) e [Discovery Server](https://turtlebot.github.io/turtlebot4-user-manual/setup/discovery_server.html) |

**Termos.** O *DDS* é o "correio" do ROS 2: ele entrega as mensagens entre os computadores. A *descoberta* (discovery) é como cada computador fica sabendo quem mais está na rede. No **Simple Discovery**, todo mundo grita na rede (multicast), e o manual avisa que isso costuma falhar em rede de universidade. No **Discovery Server**, há uma "central telefônica" no Raspberry Pi do robô. Para usar esse modo, tire o `#` da linha do `ROS_DISCOVERY_SERVER` e ponha o IP do robô.

Qual dos dois modos o robô do INF usa é pergunta para a equipe do INF (kit de campo, etapa 1). Este arquivo só configura o PC.

### 3.3 O script do modo SLAM

| | |
|---|---|
| **Onde** | `infra/docker/slam.sh` (novo) |
| **O que faz** | Sobe um container por modo (`tb4slam_sim` ou `tb4slam_robo`) e roda nele os comandos oficiais |
| **Para quê** | No dia, você roda uma linha por passo, em vez de lembrar launch, parâmetros e caminhos |

Os subcomandos, na ordem de uso:

| Subcomando | Comando oficial que roda | Fonte |
|---|---|---|
| `sim iniciar` | `ros2 launch turtlebot4_gz_bringup turtlebot4_gz.launch.py world:=maze slam:=true nav2:=false localization:=false rviz:=false` | [Navigation](https://turtlebot.github.io/turtlebot4-user-manual/tutorials/navigation.html), seção do simulador |
| `sim undock` | `ros2 action send_goal /undock irobot_create_msgs/action/Undock '{}'` (só no robô simulado) | [Docking, Create 3](https://iroboteducation.github.io/create3_docs/api/docking/) |
| `robo checar-rede` | `ros2 topic list`, conferindo `/scan`, `/tf` e `/odom` (e avisando se faltar `/battery_state` ou `/dock_status`) | [Simple Discovery](https://turtlebot.github.io/turtlebot4-user-manual/setup/simple_discovery.html) |
| `robo iniciar` | `ros2 launch turtlebot4_navigation slam.launch.py sync:=true` | [Generating a map](https://turtlebot.github.io/turtlebot4-user-manual/tutorials/generate_map.html) |
| `<modo> rviz` | `ros2 launch turtlebot4_viz view_navigation.launch.py` | Generating a map, aba Jazzy |
| `<modo> teleop` | `ros2 run teleop_twist_keyboard teleop_twist_keyboard --ros-args -p stamped:=true -p speed:=0.15 -p turn:=0.5` | [Driving](https://turtlebot.github.io/turtlebot4-user-manual/tutorials/driving.html) e o código do teleop |
| `<modo> salvar` | `ros2 service call /slam_toolbox/save_map slam_toolbox/srv/SaveMap "{name: {data: '/mapas/<nome>'}}"` | Generating a map e `slam_toolbox/src/map_saver.cpp` |
| `<modo> logs` / `parar` | Utilitários nossos | |
| `conferir <mapa>` | O nosso `conferir_mapa` (seção 3.4) | |

As escolhas que não vêm do manual, e por quê:

| Escolha | Por quê |
|---|---|
| O `sim` usa a **rede isolada** do Docker | No laboratório, o robô real está no mesmo Wi-Fi. Se o robô simulado publicasse `/cmd_vel` ou `/scan` na rede, poderia se misturar com o real. Isolado, isso não acontece |
| O `robo` usa `--network host` | O manual não fala de Docker. Sem a rede do PC, o container fica numa rede interna e não acha o robô |
| O `robo` usa `--ipc=host` | O FastDDS usa memória compartilhada entre programas da mesma máquina. Sem isso, um programa ROS rodando fora do container descobre o container, mas os dados não passam. É um problema conhecido de ROS 2 com Docker, e não está no manual |
| Teleop a 0,15 m/s e 0,5 rad/s | O padrão do teleop é 0,5 m/s e 1,0 rad/s (lido no código-fonte), rápido demais para mapear perto de gente. 0,15 m/s é o mesmo limite do INF-02. Dá para mudar com `VEL=` e `GIRO=` |
| `teleop` no `robo` pede que se digite `SIM` | Move o robô real. A confirmação lembra as condições do kit: pessoa ao lado, área livre e robô fora da doca |
| Sem undock no `robo` | Undock é ação crítica pelos guardrails. Fica à mão, pela etapa 3 do kit, como já estava |
| `salvar` com caminho absoluto `/mapas/<nome>` | O `slam_toolbox` chama o `map_saver_cli` com o nome que recebe. Com caminho absoluto, o mapa cai direto em `workspace/mapas/`. O nome só aceita `A-Za-z0-9_.-`, a mesma regra do código dele, e o script confere antes |
| `salvar` confere o campo `result` | O serviço sempre "responde", mesmo quando falha. O resultado real está em `result=0` |
| A ficha `.info.txt` | Daqui a um mês, você vai querer saber de onde veio o mapa: a data, o modo, se começou na doca e o hash do código |
| Sem simulador leve no SLAM | O leve não tem um lidar de verdade e publica sozinho a transformação `map → odom`, que é exatamente o que o SLAM calcula. Seria um teste de mentira |
| Tetos de memória: `sim` 4 GiB e `robo` 3 GiB | Regra do projeto: nada pesado sem teto. Dá para mudar com `MEMORIA=` no PC do lab |

### 3.4 Conferir o mapa

| | |
|---|---|
| **Onde** | `workspace/meu_ws/src/patrulha_tb4/patrulha_tb4/mapa_slam.py` (novo), comando `conferir_mapa` no `setup.py`, testes em `test/test_mapa_slam.py` |
| **O que faz** | Lê o par `.yaml` + `.pgm` e diz o tamanho em metros, a resolução, a porcentagem livre, ocupada e não mapeada, e o que há em (0, 0) |
| **Para quê** | Pegar um mapa ruim antes de perder tempo escolhendo pontos nele |
| **Por que assim** | Reaproveita o `ler_mapa()` e o `Mapa.estado()` do `pontos.py`. A regra de "livre" é a mesma do `validar_pontos`, então os dois não discordam |

Ele **recusa** (código 2) um mapa ilegível ou sem nenhuma célula livre: isso quer dizer que o SLAM não recebeu o `/scan`. Ele só **avisa** quando há pouca área livre (o robô mal andou) e quando a origem cai fora do mapa (então a `pose_inicial` não será (0, 0)). Ele não sabe dizer se as paredes saíram duplicadas. Para isso, abra o `.pgm` e olhe.

## 4. Como usar no laboratório

Na ordem. Só passe ao robô real depois de o treino no Gazebo dar certo.

```bash
cd ~/dev/physical_ai/Roberto/infra/docker
./construir_imagem.sh                     # só na 1ª vez

# Treino no Gazebo
./slam.sh sim iniciar                     # espere cerca de 1 min; ./slam.sh sim logs para ver
./slam.sh sim rviz                        # outro terminal
./slam.sh sim undock
./slam.sh sim teleop                      # dê uma volta pelo maze
./slam.sh sim salvar teste_maze           # deve dizer UTILIZÁVEL
./slam.sh sim parar

# Robô real: antes, etapas 1 a 3 do kit de campo, com a pessoa de segurança ao lado
./slam.sh robo checar-rede                # REDE OK?
./slam.sh robo iniciar                    # robô ainda na doca (H3)
./slam.sh robo rviz                       # outro terminal
#   undock à mão (kit, etapa 3)
./slam.sh robo teleop                     # digite SIM; ande devagar até o mapa fechar
./slam.sh robo salvar lab
./slam.sh robo parar
```

Depois: copie o `config/inf_lab.yaml`, aponte o `mapa` para `workspace/mapas/lab.yaml` e siga as etapas 5 e 6 do kit, até o `validar_pontos` aprovar.

## 6. Efeito prático

- **No laboratório**, o mapa deixa de depender de lembrar comandos: são cinco linhas, e cada uma diz se deu certo. Se algo falhar, a mensagem aponta a camada: rede (`checar-rede`), SLAM (`logs`) ou mapa (`conferir_mapa`).
- **Para a patrulha**, o mapa sai no formato que o `validar_pontos` já lê. O caminho até o L4 (o robô do INF) fica: mapa, pontos, validar, patrulha.
- **Para a equipe**, a rede do PC com o robô deixou de ser uma pendência sem script. O mesmo modelo (`--network host` com o `rede_lab.env`) serve para rodar a patrulha e o LLM no robô depois.
- **Pergunta que a banca ou o coordenador podem fazer:** "por que o robô simulado não usa a rede do laboratório?". Resposta: para não haver nenhuma chance de um comando do simulador chegar ao robô real.
